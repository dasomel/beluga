# Privileged Access Inventory and Administrative Boundaries

English | [한국어](privileged-access-inventory-ko.md)

This document establishes the privileged access inventory for the Beluga data platform, fulfilling Criterion 1 of [Issue #44](https://github.com/dasomel/beluga/issues/44) ("Privileged access paths are inventoried"). Criteria 2–5 (security-relevant privileged actions generating structured records, database access logging policy enforcement, retention/review rules, and periodic evidence reports) as well as broader Privileged Access Management (PAM) controls (MFA, session recording, approval workflows) remain open or out of scope for this inventory baseline and are not claimed as met.

## 2. Credential Boundaries and Logging Controls

### A. Zero-Secret Invariant and Runtime Generation
In accordance with [SECURITY.md](../SECURITY.md) and [docs/configuration-sources.md](configuration-sources.md), no plaintext passwords, private keys, or API tokens are checked into Git:
- **Root Credentials**: Generated by [`scripts/gitops/01-argocd-bootstrap.sh`](../scripts/gitops/01-argocd-bootstrap.sh) using `openssl rand -hex` and stored in `beluga-credentials` (`platform-system` namespace).
- **Workload Secret Isolation**: `01-argocd-bootstrap.sh` projects minimal derived Secrets into respective namespaces (e.g., `postgres-admin-credential`, `keycloak-admin-credential`, `keycloak-db-credential`, `ldap-admin-credential`, `ldap-reader-credential`, `apisix-admin-credential`, `superset-credential`, `seaweedfs-s3-credentials`, `postgres-backup-s3-credential`). Workload charts reference credentials strictly via `secretKeyRef` or `passwordSecretRef`.
- **Operator Secrets**: CloudNativePG generates `postgres-main-superuser` and `postgres-main-app` at runtime; their rotation is not established in this repository. cert-manager issues the `*-tls-secret` certificates and renews them before expiry according to each Certificate's `renewBefore` (enforced by `scripts/ci/check-certificate-inventory.py`).

### B. Audit Logging Status Across Components
Repository verification demonstrates that dedicated audit logging policies are predominantly unconfigured in the current platform manifests:
1. **Kubernetes API**: k3s runs without an `--audit-policy-file` or `--audit-log-path` argument in [`scripts/cluster/02-k8s-init.sh:27-31`](../scripts/cluster/02-k8s-init.sh#L27-L31).
2. **PostgreSQL**: Neither `pgaudit` nor connection/statement logging flags (`log_connections`, `log_disconnections`, `log_statement`) are declared under `postgresql.parameters` in [`gitops/charts/beluga-data/templates/02-cnpg.yaml:47-51`](../gitops/charts/beluga-data/templates/02-cnpg.yaml#L47-L51).
3. **OpenLDAP**: Daemon operates with standard slapd logging without the `slapo-accesslog` overlay in [`gitops/charts/beluga-platform/templates/openldap.yaml:120-160`](../gitops/charts/beluga-platform/templates/openldap.yaml#L120-L160).
4. **Keycloak & ArgoCD**: Administrative audit log destinations or external audit event forwarding are not established in this repository.
5. **APISIX**: HTTP request access logging is directed to `/dev/stdout` ([`gitops/charts/beluga-platform/templates/apisix-gateway.yaml:59`](../gitops/charts/beluga-platform/templates/apisix-gateway.yaml#L59)), but administrative change auditing is not established in this repository.
6. **Superset**: Dedicated administrative audit logging or structured export to security monitoring is not established in this repository.
