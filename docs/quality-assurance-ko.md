# Beluga 품질 보증 계획

[English](quality-assurance-en.md) | 한국어

이 계획은 요구사항 정의부터 릴리스 이후 후속 조치까지의 품질 검토 절차를 정한다.
저장소의 기존 검증과 근거를 활용하며 CI, 라이브 클러스터 테스트, 보안 검토 또는
릴리스 책임자의 최종 결정을 대체하지 않는다.

## 목표와 릴리스 기준

| 목표 | 측정 기준 | 릴리스 기준 |
|------|-----------|-------------|
| 요구사항을 검증 가능하게 관리 | 수용 기준마다 담당자와 근거 출처 지정 | 범위 내 모든 요구사항을 승인하거나 예외 기록 |
| 변경사항 검토 | PR 리뷰와 저장소 필수 검증 | 릴리스 대상 커밋에서 필수 CI 모두 통과 |
| 보안·공급망 위험 확인 | SAST, 의존성 무결성, SBOM 및 provenance 근거 | 유효하고 승인자가 명시된 위험 수용이 없는 미해결 critical 항목 0건 |
| 런타임 동작 근거 확보 | 관련 `tests/*.sh` 결과와 실행 환경 | 필수 라이브 검증 통과 또는 누락 근거를 명시한 승인 예외 |
| 결함의 명시적 종결 | 담당자, 심각도, 기한, 종결 근거 | 기록되지 않은 critical 항목을 릴리스에 포함하지 않음 |
| 재현 가능한 릴리스 근거 | 커밋, 검증 결과, 근거 참조가 포함된 생성 보고서 | 검토된 입력 파일에서 생성하고 릴리스 기록과 함께 보관 |

## 단계별 검토와 책임

| 단계 | 검토 시점과 주기 | 근거 담당자 | 검토자 |
|------|------------------|-------------|--------|
| 요구사항과 변경 범위 | 이슈/변경 패키지 승인 시 및 수용 기준 변경 시 | 이슈 또는 변경 책임자 | 제품/플랫폼 책임자 |
| 아키텍처와 보안 | 보안 경계, 런타임/도구체인, 여러 컴포넌트 변경 구현 전 | 설계 책임자 | 플랫폼/보안 검토자 |
| 구현 | 모든 PR에서 코드, 매니페스트, 문서, 회귀 범위 검토 | 작성자 | 저장소 규칙이 허용하는 경우 작성자와 다른 검토자 |
| 검증 | 모든 PR 및 정확한 릴리스 커밋에서 재검증 | 변경 책임자 | 자동 검증은 CI, 라이브 검증은 플랫폼 책임자 |
| 릴리스 준비 | 각 릴리스 또는 인계 전 | 릴리스 책임자 | 담당 보안·플랫폼·데이터 책임자 |
| 열린 품질 이슈 | 매월 및 릴리스 전 | 이슈 담당자 | 품질/릴리스 책임자 |
| 생명주기 효과성 | 분기별 및 중대 장애 이후 | 품질 책임자 | 플랫폼 책임자 |

작성자는 CI 실행 URL, 테스트 산출물, 리뷰 또는 승인 예외와 같은 영구 근거 참조와
해당 근거의 커밋을 기록한다. 정적 검증 통과는 라이브 클러스터 동작의 근거가 아니다.
게이트웨이/인증 변경은 [AGENTS.md](../AGENTS.md)에 따라 서비스 직접 접근과 문서화된
진입 경로를 모두 검증한다.

## 품질 이슈와 시정 조치 기록

각 이슈는 GitHub Issue 또는 릴리스 QA 입력 기록에서 추적한다. 고유 ID, 심각도
(`critical`, `high`, `medium`, `low`), 담당자, 기한과 다음 상태 중 하나를 기록한다.

- `open`: 시정 조치가 남아 있다. 다음 조치와 기한을 기록한다.
- `accepted`: 승인자, 사유, 만료일이 있는 명시적 위험 수용 아래 남아 있다. 만료된
  위험 수용은 릴리스 근거가 되지 않는다.
- `closed`: 종결 근거와 종결을 확인한 사람을 기록한다.

책임 있는 위험 소유자가 승인 만료 전에 위험을 명시적으로 수용하지 않으면 미해결
critical 이슈는 릴리스 준비를 차단한다. 위험 수용에는 대상 릴리스/커밋을 기록하며,
필수 검증 실패를 면제할 수 없다. 종결 근거가 해당 릴리스 커밋에 적용되지 않으면
이슈를 다시 연다.

## 릴리스·정기 QA 보고서

후보 커밋에서 실제 실행한 검증을 JSON 근거 파일에 기록한다. 입력 형식과 검증 규칙은
[`scripts/generate_release_qa_report.py`](../scripts/generate_release_qa_report.py)에
구현되어 있다. 이 도구는 검증을 실행하거나 결과를 추정하지 않는다. 각 검증에는 결과,
담당자, 근거 참조가 필요하다. 생성 결과를 다시 만들 수 있도록 입력 파일도 릴리스
기록과 함께 보관한다.

JSON 입력은 `report` 객체(`name`, `type`, 40자리 소문자 `commit`, `report_date`,
`environment`, `owner`), 비어 있지 않은 `checks` 배열(`name`, `phase`, `result`,
`owner`, `evidence`), 선택적인 `findings` 배열로 구성한다. `type`은 `release` 또는
`periodic`이며, 정기 보고서에는 `period_start`와 `period_end`도 필요하다. 검증 결과는 `pass`,
`fail`, `waived`이며, `waived`에는 승인자, 사유, 만료일이 필요하다. 각 이슈에는
`id`, `severity`, `status`, `owner`, `due_date`, `summary`가 필요하다. 종결된 이슈는
`closure_evidence`와 `verified_by`, 승인된 이슈는 승인자·사유·만료일을 포함한
`risk_acceptance`가 필요하다.

```bash
python3 scripts/generate_release_qa_report.py \
  --input path/to/qa-evidence.json \
  --output path/to/qa-report.md
```

보고서에는 기준 커밋, 검증 결과, 이슈 상태, 유효한 위험 수용, 계산된 준비 상태가
기록된다. `NOT READY`는 시정 조치 또는 유효한 위험 수용이 필요하다는 뜻이며, 릴리스
승인이 아니다. 릴리스 책임자는 보고서를 검토하고 최종 결정을 별도로 기록한다.

보고서 생성기 회귀 검증:

```bash
make test-qa-report
```
