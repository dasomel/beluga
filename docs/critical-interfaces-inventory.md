## 1. Critical Interfaces Inventory

### A. External HTTPS Interfaces via APISIX Gateway (`*.local.beluga.internal`)

All external client traffic traverses the unified APISIX Gateway entrypoint on port 443 with TLS termination backed by cert-manager certificates (`apisix-gateway-tls-secret`). HTTP port 80 requests are automatically redirected to HTTPS via an `ApisixGlobalRule` ([`gitops/charts/beluga-platform/templates/apisix-gateway.yaml:254-265`](../gitops/charts/beluga-platform/templates/apisix-gateway.yaml#L254-L265)). Host resolution across `*.local.beluga.internal` operates via two mechanisms:
1. **Wildcard DNS via dnsmasq (Primary)**: Master-1 dnsmasq wildcard-resolves `*.local.beluga.internal` to APISIX MetalLB IP `192.168.77.200` ([`scripts/cluster/10-dnsmasq.sh:80`](../scripts/cluster/10-dnsmasq.sh#L80)). On macOS developer hosts, `/etc/resolver/local.beluga.internal` delegates queries directly to Master-1 (`192.168.77.10`) without hosts file edits ([`docs/access-guide-en.md:28-42`](access-guide-en.md#L28-L42), [`scripts/up.sh:71`](../scripts/up.sh#L71)). In-cluster worker nodes forward via split-DNS ([`scripts/cluster/10-worker-dns.sh:32-42`](../scripts/cluster/10-worker-dns.sh#L32-L42)), and Pods resolve via CoreDNS forwarding ([`scripts/cluster/10-dnsmasq.sh:127-147`](../scripts/cluster/10-dnsmasq.sh#L127-L147), [`docs/access-guide-en.md:22`](access-guide-en.md#L22)).
2. **Managed `/etc/hosts` block (Alternative)**: `bash scripts/hosts.sh --apply` ([`scripts/hosts.sh:69-80,160-172`](../scripts/hosts.sh#L69-L80), [`docs/access-guide-en.md:43-62`](access-guide-en.md#L43-L62)) dynamically registers all 10 domain variables defined in [`configs/cluster.env:35-47`](../configs/cluster.env#L35-L47) pointing to `192.168.77.200` ([`configs/cluster.env:18,36`](../configs/cluster.env#L18), [`scripts/hosts.sh:39`](../scripts/hosts.sh#L39)).

*Host Setup Discrepancy Note*: The convenience `/etc/hosts` example in [`AGENTS.md:28-31`](../AGENTS.md#L28-L31) lists only 7 domains mapped to `127.0.0.1` and omits `filer`, `flink`, and `metadata`. For `filer`, `flink`, and `metadata` (rows 24–26 below), the repository provides APISIX route manifests and domain definitions, but no host entry is documented in the `AGENTS.md:28-31` snippet; these three HTTPS endpoints are therefore not resolvable from that static snippet alone unless using dnsmasq resolver delegation or `scripts/hosts.sh --apply`.

## 2. Integration Governance and Contract Observations

### A. Edge Routing and Ingress Demarcation
- **Single Edge Entrypoint**: All external HTTP/HTTPS requests terminate at the APISIX Gateway on port 443 with TLS certificates issued by cert-manager via the `beluga-internal-ca-issuer`. HTTP port 80 requests are redirected to HTTPS across all domains.
- **Host Resolution Boundary**: Client resolution of `*.local.beluga.internal` relies on Master-1 dnsmasq wildcard resolution ([`scripts/cluster/10-dnsmasq.sh:80`](../scripts/cluster/10-dnsmasq.sh#L80)) or managed hosts blocks ([`scripts/hosts.sh:69-80`](../scripts/hosts.sh#L69-L80), [`configs/cluster.env:35-47`](../configs/cluster.env#L35-L47)). The minimal `/etc/hosts` snippet in [`AGENTS.md:28-31`](../AGENTS.md#L28-L31) omits `filer`, `flink`, and `metadata`; route definitions exist for all three, but host entry resolution requires dnsmasq delegation or `scripts/hosts.sh --apply` rather than the `AGENTS.md` snippet.
- **Upstream Network Isolation**: APISIX routes connect to internal services using cluster DNS names (`<service>.<namespace>.svc.cluster.local`). In-cluster Cilium and Kubernetes NetworkPolicies restrict inter-namespace ingress to authorized caller workloads.
- **Rate Limiting Baseline**: Route rate-limiting policies for public ingress are governed and tracked against the frozen baseline in [`scripts/ci/check-apisix-route-rate-limit.py`](../scripts/ci/check-apisix-route-rate-limit.py) (Issue #48).

### B. In-Cluster Service Authentication and Authorization Boundaries
- **Zero-Secret Invariant**: In accordance with [SECURITY.md](../SECURITY.md) and [docs/configuration-sources.md](configuration-sources.md), no plaintext credentials are saved in Git; all runtime tokens and passwords derive from root bootstrap credentials (`beluga-credentials`) or operator-managed controllers.
- **Lakekeeper REST Authorization Transition**: In the current repository baseline, Lakekeeper runs with `LAKEKEEPER__AUTHZ_BACKEND="allowall"`, providing unauthenticated catalog operations across internal consumers. Open PR #159 proposes enabling OpenFGA fine-grained authorization and Keycloak OIDC authentication; however, until PR #159 is reviewed and merged into `main`, this unmerged behavior is not current platform behavior.
- **OpenMetadata Ingestion Pipeline Status**: Manifests in [`gitops/charts/beluga-data/templates/11-openmetadata.yaml`](../gitops/charts/beluga-data/templates/11-openmetadata.yaml) establish the core server and OpenSearch backend, but scheduled metadata ingestion pipelines/connectors (e.g., harvesting schemas from Trino, Kafka, or Lakekeeper) are *Not established in this repository*.

### C. Contract Versioning and SLA Status
- Component versions are governed exclusively by [VERSIONS.md](../VERSIONS.md).
- Formal contract artifacts (OpenAPI schemas, Protobuf/Avro registries for Kafka event streams, backward-compatibility SLAs, and formal deprecation schedules) are *Not established in this repository* and remain subject to subsequent passes under Issue #22.
